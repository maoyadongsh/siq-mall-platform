# 项目检查与商业化优化建议

2026-11-06。检查范围：源码、配置、部署模板、原设计文档、本机测试与构建、真实MariaDB/Redis探针。未执行完整渗透测试、负载压测或生产服务器检查。

## 1. 总体判断

当前项目是可继续开发的框架演示，尚不是可经营的商城。优点是前后端分离、分环境配置、统一响应、JWT骨架和基础测试齐备。主要差距在交易闭环、运营工作台、体验设计和可证明的发布能力。维持模块化单体是合理选择，暂不需要微服务。

## 3. 产品体验建议

商城：首页采用品牌主视觉、分类入口、精选商品、服务承诺；商品卡突出图片、价格、规格与可售状态，不使用虚构销量。搜索筛选同步URL，返回列表恢复筛选和滚动位置。详情覆盖未选规格、缺货、下架、价格更新等状态。

结算：商品、运费、优惠、实付分项展示；价格变化重新确认；失败保留选择；服务端幂等保证重试不多单。订单用时间线说明支付、发货、收货、取消。

后台：独立布局和权限，提供商品批量维护、待发货订单视图、优惠券占用/核销统计、CMS草稿预览、客服待回复队列。重要操作记录操作者、前后值和时间，不以Django Admin等同完整运营工作台。

设计token统一颜色、间距、字号、圆角和动效；375/768/1440px、键盘操作、空态/加载/错误状态都需截图验收。不以增加动画与图表替代可用性。

## 4. AI能力建议

优先引入商品文案草稿、属性补全建议、评价主题摘要和客服回复草稿。模型不直接改价、扣库存、退款或取消订单。商业价值由人工采纳率、事实准确率、客服处理时间和每次成本验证。

后端AI网关负责脱敏、权限过滤、限额、审计；检索只读取当前角色可见资料，输出带来源与版本；结构化输出校验后进入人工确认，再调用确定性业务服务。上传文本视为数据，不能允许提示注入越过权限。

建立固定评测集：事实准确、引用可追溯、跨用户泄露、拒答转人工、P95延迟、成本。AI可关闭且不阻塞交易链路；在商城稳定后独立排期，不扩大当前基础框架范围。

## 5. 发布与后续判断

现有目录不是Git仓库，本轮没有commit级变更基线，也未初始化Git、提交代码或修改业务数据。后续确认.env忽略规则后建立版本管理。

不建议现在引入微服务、Kubernetes或推荐系统。优先完成可信交易、履约、运营、备份恢复和设计验收。SQLite通过不等于并发正确，构建通过不等于浏览器体验通过，演示支付成功不等于可商业收款。
